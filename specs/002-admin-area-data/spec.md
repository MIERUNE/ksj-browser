## Clarifications

### Session 2026-01-11

- Q: 行政区域データの定義に含める配布形式（SHP/GML）はどう選ぶ？ → A: SHP があれば SHP、なければ GML
- Q: 行政区域データの「地域」キー（都道府県名表記）はどうする？ → A: 既存コレクションと同じ表記（原則サフィックス無し）
- Q: データ更新ツールが生成する年度範囲はどうする？ → A: 掲載されている全ての年度を生成・更新する
- Q: 行政区域データのコレクション ID はどうする？ → A: gyousei_kuiki
- Q: 生成した定義ファイルの運用方針はどうする？ → A: リポジトリにコミットして同梱（実行時はローカル定義を読む）

※補足: 「既存コレクションと同じ表記」は、都道府県名（例: `青森県`, `東京都`, `京都府`, `北海道`）を指す。`全国` のようなキーも存在し得る。

## NLFTP GML ダウンロード URL 規則（N03: 行政区域）

このプロジェクトでは「年（例: `2025年`）」と「ファイル名（例: `N03-20250101_01_GML.zip`）」から、NLFTP の ZIP ダウンロード URL を組み立てる。

### URL の基本形

- ベース: `https://nlftp.mlit.go.jp/ksj/gml/data/{DATA_ID}/{DIR}/{FILENAME}`
- `DATA_ID`: ファイル名先頭の ID（例: `N03`）
- `FILENAME`: datalist ページ上の ZIP 名（例: `N03-20250101_01_GML.zip`）

### N03 のディレクトリ規則

- `DIR` は常に `N03-{YYYY}` の 4 桁年（例: `N03-2025`）
- ファイル名内の年表現は揺れる（例: `20250101` / `071001` / `06` など）ため、ディレクトリ年は原則「入力として与えた year（`YYYY年`）」から決める

#### 正規化ルール（実装側の期待）

- `year` は `YYYY` を含む文字列（例: `2025年`）
- `filename` は `{DATA_ID}-...(.zip)` 形式（例: `N03-20250101_01_GML.zip`）

### 例

- `year=2025年`, `filename=N03-20250101_01_GML.zip`
  - `https://nlftp.mlit.go.jp/ksj/gml/data/N03/N03-2025/N03-20250101_01_GML.zip`
- `year=2006年`, `filename=N03-06_01_GML.zip`
  - `https://nlftp.mlit.go.jp/ksj/gml/data/N03/N03-2006/N03-06_01_GML.zip`

### 他データとの違い（A33 等）

- A33 等の多くのデータは `DIR` が `{DATA_ID}-{YY}`（2 桁年）になり、ファイル名の先頭トークン（例: `A33-24_...` の `24`）から決められる
- N03 は `{YYYY}` 固定のため、同じロジックを流用するとディレクトリが不正になり得る

## User Scenarios & Testing _(mandatory)_

### User Story 1 - データ更新ツールの実行 (Priority: P1)

開発者が行政区域データの最新版が公開されたときに、Web サイトから情報を取得してデータコレクション定義ファイルを更新したい。ツールを実行するだけで、手動で Web ページをコピー&ペーストする必要なく、自動的に最新のデータコレクション定義を生成できる。

**Why this priority**: これは MVP の中核機能であり、データ更新の自動化がこの機能の主要な価値提供。手動作業の削減が最も重要な要件。

**Independent Test**: ツールを実行し、データコレクション定義ファイルが生成され、Web サイトと同じ内容が含まれることを確認できる。

**Acceptance Scenarios**:

1. **Given** 開発者がプロジェクト環境にいる、**When** データ更新ツールを実行する、**Then** 行政区域データのコレクション定義ファイルが作成または更新される
2. **Given** 国土数値情報の Web サイトに N03（行政区域）データが公開されている、**When** ツールを実行する、**Then** 定義ファイルには年度ごと・地域ごとのファイル名が正しく格納される
3. **Given** 定義ファイルが既に存在する、**When** ツールを再実行する、**Then** 既存のデータは最新の情報で上書きされる

---

### User Story 2 - ブラウザパネルでの行政区域データの表示 (Priority: P2)

QGIS ユーザーがブラウザパネルを開いたときに、既存の土砂災害警戒区域データと同様に、行政区域データもツリー構造で表示され、選択してダウンロード・読み込みできる。

**Why this priority**: スクリプトでデータ定義を生成した後、それを実際に使用できるようにする必要があるが、これは P1 の成果物に依存する。

**Independent Test**: QGIS でブラウザパネルを開き、KSJ プロバイダーのセクションに「行政区域」が表示され、年度と地域を選択してデータを読み込めることを確認できる。

**Acceptance Scenarios**:

1. **Given** データコレクション定義ファイルが存在し、表示名が登録されている、**When** ブラウザパネルを開く、**Then** 「土砂災害警戒区域」と「行政区域」の両方がルートアイテムとして表示される
2. **Given** ブラウザパネルで「行政区域」を展開する、**When** 年度を選択する、**Then** その年度に対応する都道府県リストが表示される
3. **Given** 特定の都道府県を選択する、**When** ダブルクリックまたはドラッグ＆ドロップする、**Then** 該当する地図データがマップキャンバスに読み込まれる

---

### Edge Cases

- Web サイトの構造が変更された場合、ツールはどのように動作するか？（エラーメッセージを表示し、開発者に手動確認を促す）
- 年度や地域のデータが一部欠落している場合はどうなるか？（利用可能なデータのみを定義ファイルに含め、欠落データは警告ログに記録）
- 定義ファイルの形式が壊れている場合、ブラウザパネルはどう振る舞うか？（エラーをログに記録し、該当コレクションをスキップして他のデータは表示を続ける）
- 同じ年度・地域に対して異なるファイル名が存在する場合はどうするか？（最初に見つかったものを使用し、警告をログに記録）
- 同じ年度・地域に SHP と GML の両方がある場合はどうするか？（SHP を優先し、SHP がない場合のみ GML を採用する）

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: システムは国土数値情報 Web サイトの N03（行政区域）データページから、年度・地域・ファイル名の情報を自動抽出できなければならない
- **FR-002**: システムは抽出した情報を、既存の土砂災害警戒区域データと同じ構造のデータコレクション定義ファイルとして保存できなければならない
- **FR-003**: 開発者はツールを実行するだけで、データコレクション定義ファイルを生成または更新できなければならない
- **FR-004**: ツールは実行時のエラー（Web サイトアクセスエラー、パース失敗など）を適切に報告しなければならない
- **FR-005**: 生成されたデータコレクション定義ファイルは、プロジェクトの適切な場所に配置されなければならない
- **FR-006**: システムは行政区域データの表示名（例：「行政区域」）を管理できなければならない
- **FR-007**: ブラウザパネルは、新しく追加された行政区域データコレクションを、土砂災害警戒区域と同じ方法で表示できなければならない
- **FR-008**: ユーザーは行政区域データを年度・地域で絞り込み、選択したデータを地図に読み込めなければならない
- **FR-009**: ツールは既存の定義ファイルが存在する場合、それを上書き更新できなければならない
- **FR-010**: 生成されたデータコレクション定義の構造は、年度と地域でグループ化され、各地域に対応するファイル名が含まれなければならない
- **FR-011**: 年度・地域に対して複数の配布形式が提示される場合、ツールは SHP を優先し、SHP が存在しない場合のみ GML を採用しなければならない
- **FR-012**: 地域名キーは既存コレクションと同じ表記を用いなければならない（例: `青森県`, `東京都`, `京都府`, `北海道` など）
- **FR-013**: ツールは Web サイトに掲載されている行政区域データの全ての年度を抽出し、定義ファイルに含めなければならない
- **FR-014**: 行政区域データのコレクション ID は `gyousei_kuiki` でなければならない
- **FR-015**: データコレクション定義ファイル名はコレクション ID に一致しなければならない（例: `gyousei_kuiki` → `gyousei_kuiki.json`）
- **FR-016**: 行政区域データの定義ファイルはリポジトリにコミットされ、実行時は同梱されたローカル定義を参照しなければならない
- **FR-017**: ダウンロード URL 生成ロジックは、20 以上のデータコレクション追加を想定し、データ ID ごとの戦略を容易に追加できる拡張可能な設計でなければならない

### Assumptions

- 国土数値情報の Web サイト構造は、大幅な変更がない限り現在の形式を維持する
- 行政区域データのファイル名規則は、土砂災害警戒区域と同様の命名パターンに従う
- ツールは開発環境で実行され、必要な依存関係はインストール済みとする
- データコレクション定義ファイルは標準的なテキストエンコーディング（UTF-8）を使用する
- ツールはプロジェクト内の適切な場所に配置される
- ブラウザパネルでの表示ロジックは、既存のデータ読み込みとブラウザ表示の仕組みを再利用する
- Web サイト上の地域名表記が異なる場合でも、ツールは既存コレクション表記に正規化できる

### Key Entities

- **DataCollection（データコレクション）**: 特定のデータセット（例：行政区域）を表し、年度ごとの地域別ファイル情報を保持する
- **YearlyData（年度別データ）**: 特定の年度における全地域のファイル情報を保持する（例：「2024 年」の全都道府県データ）
- **RegionalFile（地域別ファイル）**: 特定の地域（都道府県）とそのダウンロードファイル名の対応を表す（例：「北海道」→「N03-24_01_GML.zip」）

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 開発者がツールを実行してから 30 秒以内に、行政区域データのコレクション定義ファイルが生成される
- **SC-002**: 生成された定義ファイルには、Web サイトに公開されている全ての年度と地域のデータが含まれ、データの欠落率が 0%である
- **SC-003**: ブラウザパネルで行政区域データを選択してから 5 秒以内に、地図キャンバスにデータが表示される
- **SC-004**: 手動でのデータ定義更新作業が 100%削減され、開発者はツール実行のみで最新データに対応できる
- **SC-005**: エンドユーザーは、土砂災害警戒区域と同じ操作感で行政区域データを利用でき、操作方法の学習コストが発生しない
